## 6A. Reactive cost guard and balance-aware cascade

These are additional owner-requested requirements in this draft, not delivered behavior. Preflight evidence/free-only enforcement remains mandatory. The owner authorized short tests of the supplied accounts without billing details; that is not a persistent machine-readable free certificate or permission to deliberately incur charges.

### Response monetary normalization

Inspect the original upstream buffered object before recording success, synthesizing token usage or returning content. Inspect every decoded SSE object before forwarding it, including usage-only/final objects with empty choices. A usage-only event must never escape inspection because it lacks delta.content.

Initial documented monetary mapping: OpenRouter usage.cost is the amount charged to the operator's account, in provider-defined credits/USD semantics. Its cost_details.upstream_inference_cost is a distinct payer/cost and must not be labeled an operator charge. Token counts, durations, catalog rates, estimates, sponsored upstream spend, consumption of included free allowance and missing/null cost are not automatically actual paid operator charge signals; each monetary profile must establish its unit and payer semantics. Other profiles initially report monetary reporting unavailable unless an exact documented field/unit/payer mapping is added to the source contract; do not scan arbitrary field names called cost. Synthetic token usage must never synthesize a zero monetary charge.

Parse recognized monetary values with exact finite nonnegative Decimal semantics; numeric strings/scientific notation may be accepted, bool/NaN/infinity/negative/malformed values are invalid. Keep fixed normalized outcomes unavailable, zero, positive and invalid. Missing/null fields where the source permits them are unavailable. Unavailable reporting does not independently certify or revoke sufficient preflight evidence. Invalid recognized billing data latches the guard with a fixed unverifiable_cost diagnostic and uses the same completion/output policy as positive cost; it must not be treated as zero or an established invoice amount. A positive actual operator charge triggers unexpected_paid_cost.

### Shared billing incident state

Guard scope is provider ID + normalized inference endpoint + credential epoch, or the explicit anonymous profile identity when no key exists. This is the credential scope known to the service; do not claim all keys of an unknown common account are identifiable. A billing incident invalidates/freezes admission for every model in that scope, not just the triggering model. New queued/failover dispatches recheck this guard immediately before HTTP work and skipped held candidates do not consume attempt budget. Close/cancel locally owned incomplete upstream work for the held scope best effort, using the output-state policy below for each affected request. Preserve complete valid triggering and concurrent responses for normal delivery, including pending terminal SSE framing; cancellation must not destroy them. Already-sent/concurrent requests may have incurred charges and remote cancellation is not guaranteed. Publish the hold before making any new dispatch decision; capture/retain a complete response before cancellation callbacks can discard it.

unexpected_paid_cost and unverifiable_cost are latched for the current process/credential binding. Catalog/evidence success, ordinary model cooldown and a successful concurrent request cannot clear them. They are not retried by an automated inference probe. Observed credential/endpoint changes create a new scope that still requires fresh sufficient eligibility; an operator restart also begins with no admission until fresh evidence exists. No durable billing-incident database or claim of persistence across restart is added in this scope. Fixed safe reasons/times appear in in-memory status/probe output; no stable key fingerprint, prompt, generated text, provider error body or arbitrary account identifier is logged.

### Output boundary and terminal telemetry

Evaluate response state in the following order: COMPLETE, then NOT_STARTED, then IN_PROGRESS. Completion takes precedence even when nothing has yet reached the consumer. The billing guard is updated in every case; delivery success and a billing incident are separate outcomes.

| State at incident | Consumer behavior | Upstream/cascade behavior |
|---|---|---|
| COMPLETE — a complete valid answer is available | Return the buffered answer normally, or finish the current SSE normally with exactly one DONE. Do not inject a billing error or discard useful output. | Latch the scope; release upstream resources normally. No replacement generation for this answer. |
| NOT_STARTED — incomplete answer and no semantic output forwarded | Try another eligible provider within the existing attempt/deadline budget. If exhausted, return the existing safe exhausted/budget error envelope. | Cancel/close the incomplete upstream first; scope holds apply to every candidate recheck. |
| IN_PROGRESS — incomplete answer with semantic output already forwarded | Never restart or replay text/tools/reasoning. If the guard stops the incomplete stream, send one fixed redacted error event and close without successful DONE. | Cancel/close incomplete upstream; no second provider for this answer. |

For buffered delivery, COMPLETE means the full valid successful completion object is received and protocol validation succeeds. For SSE, COMPLETE requires a valid terminal finish_reason for the single supported choice (including normal tool_calls/length finishes), or a valid upstream DONE after a valid completion sequence, with no observed generation error. A role-only/content fragment or an arbitrary EOF is insufficient. A usage-only cost object after terminal finish therefore preserves normal completion. Use the existing supported choice cardinality; do not broaden it here. A real upstream generation error remains a failed response and cannot be turned into success by this exception. Once terminal completion is established, the stream owner inspects remaining final usage/framing while retaining the completed answer; it must not cancel its own finalization solely because the cost guard fired. Existing stream time/resource bounds still apply; no unbounded drain or extra inference request is allowed.

Role-only chunks do not count as semantic output. Nonempty content, tool/function-call deltas, reasoning/reasoning_details and other already-forwarded semantic payloads do. Headers/heartbeat comments alone are not semantic output; adapter/router must track actual forwarded semantic output consistently. Cost first detected in a terminal event is classified after validating that event's completion state, before any hold-triggered cancellation. A complete buffered response with positive cost follows COMPLETE, not NOT_STARTED.

Only an interrupted incomplete SSE uses the event data: {"error":{"type":"billing_guard_error","code":"unexpected_paid_cost" or "unverifiable_cost" or "billing_unavailable","message":"Upstream billing guard stopped this response."}}. Do not place raw provider diagnostics, cost payloads or secret-derived identifiers in it. Headers may already be HTTP 200; the event and terminal trace identify the interrupted answer as failure. A complete delivered answer has no consumer-visible billing error.

A late usage/error must reach the shared guard even after stream ownership was handed to the response wrapper; silently swallowing it is forbidden. The stream owner finalizes exactly one trace through the preserved _record_trace_safely path: successful complete delivery has success=true even when a cost incident was detected, while interrupted/failed delivery or downstream cancellation is unsuccessful. Record the independent incident with its fixed reason and safe scope/time in in-memory guard/probe status and a redacted structured operational log; do not add telemetry schema/store fields or a conflicting second request trace. Successful delivery never clears the cost latch. This explicitly replaces the delivered early-handoff success timing without changing field names/privacy contracts.

### Billing-error classification and fixed recovery

Classify fixed provider status/error metadata, never an arbitrary substring quota. Initial mappings:

| Provider signal | Normalized outcome / scope |
|---|---|
| OpenRouter HTTP/SSE error 402 with limit_source=openrouter_in_flight_budget | billing_temporarily_unavailable; transient shared credential-scope hold, not proof of an empty wallet |
| OpenRouter ordinary documented insufficient-credit 402 with no limit_source (the separately mapped in-flight case has priority) | insufficient_balance_or_budget; shared credential-scope hold |
| OpenRouter 403 with limit_source=openrouter_guardrail_budget, openrouter_workspace_budget or openrouter_key_limit | insufficient_balance_or_budget; shared credential-scope hold; ordinary permission 403 remains distinct |
| Mistral HTTP/SSE error 402 under its documented credit/included-usage contract | insufficient_balance_or_budget; shared credential-scope hold |
| Unknown provider 402 without established semantics | billing_access_unverified; conservative shared credential hold, no assertion about exact wallet cause |
| Ordinary 403 without a mapped billing code | Existing auth/permission error behavior; do not assert balance exhaustion |
| Ordinary rate-limit 429 | Existing rate-limit handling unless documented provider metadata establishes a different specific quota scope |

Pin these exact documented metadata values in fixtures. Unknown or ill-typed OpenRouter 402 limit_source values remain billing_access_unverified; unknown 403 metadata does not become a guessed billing classification. Check HTTP errors and in-stream error objects before semantic output; body-level 402 must not become an unrelated 502 or heuristic rate-limit 429.

A non-latched balance/transient hold defaults to 60 seconds. Honor a valid Retry-After (seconds or HTTP date) within 1..300 seconds; absent/invalid values use 60. Do not sleep a client request through the hold: immediately attempt another eligible provider. After expiry, at most one new user-request attempt in that scope may recheck upstream availability, and only with fresh adequate eligibility; other concurrent requests skip it. Success clears only that non-latched hold; repeated failure renews it. No background paid probe, account top-up, plan change or model sweep. A latched cost incident always wins over balance recovery. This is fixed billing-scope recovery only; exponential/adaptive provider auth recovery remains T-009.

Financial limit: a charge reported after generation cannot be refunded or prevented retroactively by this guard. Some providers do not expose monetary cost; some streaming costs arrive only at the final event. This mechanism limits subsequent requests and closes work where possible; it cannot guarantee zero loss for in-flight work or substitute for admission/free-only controls.
